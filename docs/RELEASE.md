# 发布准则

本文件是发布范围与交付流程的长期规则。用户对本轮发布的明确指令优先；未明确变更时沿用本规则。验收契约见 [ACCEPTANCE.md](ACCEPTANCE.md)，红绿重构流程见 [REFACTORING.md](REFACTORING.md)。历史版本记录不代替当前规则。

## 平台与架构

- Android **只构建、只发布 arm64-v8a**。不额外构建 armeabi-v7a、x86_64 或包含多架构的通用 Release APK；不能只在上传时隐藏另外两个包。
- 固定构建命令：`sh tool/flutterw.sh build apk --release --target-platform android-arm64 --split-per-abi`。
- 唯一发布资产：`tingyu-<版本>-android-arm64-v8a-release.apk`。`tool/release-apks.json` 的 `apks` 数组只能包含这一项，APK 内的 `lib/` ABI 集合必须精确等于 `{arm64-v8a}`。
- 历史输出目录可能留有其他架构的旧包。不得用 `*-release.apk` 通配符上传；逐个指定本轮清单中的文件。旧文件存在不代表本轮构建或验收通过。
- macOS、Windows 的设计、图标、打包和发布只有在用户明确要求时开展。现有手动 Native checks 包含桌面编译检查，不代表授权发布桌面产品，也不代表桌面实机验收。
- GitHub Release、应用商店上传和签名变更均需本轮用户授权；本规则本身不构成以后自动发布的授权。

## 文档同步是发布门禁

每次发布（包括仅修复版本）均须在发布前核对并实时更新 README：版本、实际功能、运行截图、唯一 arm64-v8a 下载入口及已知限制必须与本次最终提交和 APK 一致，不能发布后再补。README 未同步即停止发布。

有新增、变更或移除功能时，以下内容也必须与最终提交、APK 的行为一致：

| 文档 | 本次发布必须更新的内容 |
|---|---|
| [FEATURES.md](FEATURES.md) | 功能 ID、入口、状态/错误恢复、持久化和取消/删除语义、能力边界；移除能力明确标记 |
| [ACCEPTANCE.md](ACCEPTANCE.md) | 新增/变更的可判定条件、状态矩阵、对应自动/原生/人工证据；不得降低原有契约来迎合实现 |
| [UI.md](UI.md) | 涉及风格/布局/动画/图标时更新已确认基线及来源，保留视觉前后对照；取消的方案不再作为现状 |
| 版本专项验收文档 | Red/Green/Refactor（如适用）、命令、结果、环境、截图、指纹、待验与未关闭问题 |
| README、Release 说明和发布清单 | 版本、最终范围、架构、签名类别、验证限制、下载入口与 SHA-256 |

发布前逐项检查：代码有变化而功能清单/验收仍停留在旧行为，或视觉更新尚未确认/记录时，不进入上传步骤。确实不适用的文档项写明无需变更的原因，不做无意义改字；纯修复也要在结果记录和发布说明说明回归范围。记录“已实现”和“已验收”时必须区分，不能把计划功能、夹具结果或取消方案写成已完成。

## 版本、签名和数据

- 发布前同步 `pubspec.yaml`、`lib/ui/settings_views.dart` 版本文案、发布清单、标签和说明。Android 版本号必须递增；arm64 拆分包 versionCode 为 `2000 + pubspec build number`，由校验脚本核对。
- 现有安装包使用开发/debug 签名，发布说明必须如实注明，不能称为商店正式签名。升级包须使用同一证书；证书指纹由 `tool/verify_android_release.py` 验证。
- 不用卸载、清数据或换签名解决覆盖安装失败。用户设备仅允许同签名 Release 的 `adb install -r`；自动测试只运行在隔离的 `tingyu-regression / emulator-5558`。
- 签名私钥、登录 Cookie、Apple 资料、临时音频 URL、SDK、build 和 artifacts 不提交 Git。APK 作为 Release 资产交付。

## 本地发布执行顺序

以下命令从项目根目录执行；Windows 应按已验证的本机工具链使用对应命令，不把 Mac 结果当作 Windows 结果。

1. 明确本轮需求、已确认视觉和取消项。检查工作区，保留用户改动；按 [验收标准](ACCEPTANCE.md) 确定必测项及人工项。
2. 完成最终代码、Android 图标资源和版本更新。`tool/generate_app_icons.py` 只生成 Android 图标，不改桌面资源。Flutter 测试、drive 和 Release 构建顺序执行，避免生成的插件注册文件在构建过程中被另一条 Flutter 命令改写。
3. 执行最终源码验收：

   ```sh
   python3 tool/run_acceptance.py --device emulator-5558 --live
   ```

4. 全部适用工程门禁通过后，仅构建 arm64：

   ```sh
   sh tool/flutterw.sh build apk --release --target-platform android-arm64 --split-per-abi
   python3 tool/verify_android_release.py
   python3 tool/check_android_fullscreen.py --device emulator-5558 --apk build/app/outputs/flutter-apk/app-arm64-v8a-release.apk
   ```

5. 核对同一份 APK 的 ZIP 完整性、包名、版本、唯一 ABI、签名、大小和 SHA-256。`fullscreen.json` 的 `apkSha256` 必须等于发布清单。图标改动额外核对 APK 内实际图标的透明遮罩、可见线条和启动器截图；AAPT 可能重命名资源及重编码透明像素，不能仅按文件名或透明像素的 RGB 判断图标相同。
6. 保存同源 `report.json`、系统栏结果、截图与发布清单，文档写明命令、结果、源码指纹、包 SHA 和未验范围。`run_acceptance.py` 不负责 G03/G08 全部检查，`humanHandoffReady: false` 也不会因脚本退出码为零自动变为人工通过。不得把未执行项补成 PASS。
7. 将确认的代码、图标母版、文档和清单提交为一个可追溯状态，标签指向该提交。测试用来证明的源码和构建资源发生变化后重新执行适用门禁；不能直接沿用旧版本报告。当前源码指纹不覆盖全部 docs、branding 母版和工具脚本，这些文件仍须通过 Git 提交和独立校验追溯，不能把指纹当作全仓库证明。
8. 按下方“发布说明固定结构”及模板完成正文并逐项核对；经用户授权后推送源码和版本标签，创建 Release，仅上传清单中的 arm64 APK。说明包含改动、开发签名、验证范围、已知限制和 SHA-256。
9. 从 GitHub 回读，检查正文结构与下载表格链接，再核对 Release 非草稿、标签指向验收提交、资产数为 1、文件名/大小正确，服务端 `digest` 等于本地 SHA-256。上传失败保留草稿排查，不宣称发布完成，不重复创建同版本 Release。

## 发布说明固定结构

每次 Release、测试包交付和对外版本公告均按以下顺序编写，使用 [发布说明模板](RELEASE_TEMPLATE.md)，不以提交日志代替面向用户的说明：

1. **一句话总结开头**：正文第一段用一句话概括本版主要变化和用户收益，不先放版本元数据、下载链接或标题。
2. **功能点列表**：标题为“功能”，列出本版新增或扩展的能力，写清用户能做什么。
3. **优化与修复点列表**：标题为“优化与修复”，列出体验优化、缺陷修复和必要的兼容变化，与功能列表不重复。
4. **“我要下载哪个版本？”表格**：标题必须使用此原文；表格列为“设备／场景”“应下载的文件”“说明”，文件名链接到本次实际资产。

功能或优化修复某项为空时，仍保留该段，以一条“本次无新增功能”或“本次无单独优化与修复”说明，不编造内容。表格只列本轮实际提供的包；当前仅一行Android arm64-v8a，不暗示提供其他架构、通用包或桌面包。设备说明以ABI为依据，不把所有Android设备都称为支持。

这四部分之后再放必要的“安装与验证说明”：开发/debug签名、同签名覆盖升级及数据保留、实际验证范围、已知限制、待验项和完整SHA-256。下载不兼容设备明确说明本轮未提供适用包。不能为了精简发布文案省略现有发布门禁要求。

发布前逐项检查：

- 第一句为一句话总结，后面严格依次为功能列表、优化与修复列表、下载选择表格。
- 各项只包含本轮真实实现并有证据的变化，计划项、原型、取消方案不冒充已发布功能。
- 表格文件名、下载链接、版本、架构与release-apks.json及实际上传资产一致，当前仅arm64-v8a一项；本地未上传的测试包链接到实际交付文件。
- 安装、签名、验收边界与SHA-256完整，文档同步门禁已满足；发布后回读最终正文及链接，确认与上传资产对应。

## 验收与发布的边界

- 工程门禁失败或必需项未运行时，不能作为“已验收包”交付。真实网络失败单独记录原因，不能改用夹具后宣称真实服务通过。
- 允许在用户明确授权的开发版发布中保留已披露的真机待验项；必须逐项写明，不得称为全平台或全场景通过。物理设备的听感、蓝牙、来电、锁屏与厂商省电不能由模拟器替代。
- 应用图标母版为透明底白色柔角线条；系统启动器可能加遮罩或底板。Pixel 模拟器显示圆形底板是已观测的启动器表现，不应把它绘制进母版，也不能保证所有手机桌面完全相同。
- 纯文档、注释或 CI 命令范围调整：检查链接、命令和差异，必要时检查工作流语法；不重复构建、上传 APK，不把未运行的移动端测试写成此次结果。发布流程本身的代码变更仍需对应验证。
