# 封面缓存并发清理修复

状态：已完成修复、验收与发布。用户授权范围内的 0.1.36 Mac/Android 资产已公开，验证边界见版本验收记录。

## 目标与证据

修复搜索推荐中图片已完整缓存却持续显示波形占位的问题。真实样本 `BV179WW6oESh` 的网络 JPEG 与本机缓存 SHA-256 相同，Flutter 可正常解码；本机封面缓存约 63.7 MiB，接近 64 MiB 上限。

已在隔离目录复现：预放 64 MiB 旧缓存，四个封面请求并发完成；旧实现有三次 `get` 返回 null，但对应文件与 `peek` 有效，再次获取成功。原因是多次 `_trim` 同时删除同一旧文件，异常被 `_load` 误认为图片加载失败。证据：`artifacts/cover-20261111/diagnosis.json`。

## 边界与方案

- 沿用共享 `CoverCache`，串行执行完整缓存清理（枚举、排序、删除、内存索引更新）；保留最多四个并发图片传输。
- 图片成功落盘后，缓存清理的 `FileSystemException` 记录为维护错误，不改写成功加载结果；后续维护可继续。网络/下载写入失败仍返回 null，未知编程错误不静默吞掉。
- 关闭仍取消网络请求并等待已启动的加载和维护结束。
- 保持 URL 身份、64 MiB LRU、文件路径及现有数据；不新增兼容层、平台分支、图片重试框架或数据库迁移，不修改布局。
- 同一逻辑覆盖 Mac/Android/Windows。Mac/Android 执行原生渲染验证；Windows 无本机运行环境，源码/共享测试与原生未验分别记录。

## 验收标准

1. 达到容量上限时，四路并发下载首次均返回真实有效图片，`peek` 与结果一致；旧文件淘汰、最终缓存不超限，重复获取不增加请求。
2. 单次旧文件清理失败可观测，已落盘图片仍返回成功；故障消除后下一次维护恢复淘汰，不阻塞队列。
3. 网络失败语义、请求去重、四路传输限制、CDN 等价地址与重启复用保持；关闭等待和取消不回归。
4. 原生实际封面组件在容量边界并发加载后均完成解码，无需点击、切页或再次请求才能显示。
5. 最终源码通过仓库工程门禁；发布 0.1.36+37 的 Mac DMG 与 Android arm64 APK，验证包、签名、源码指纹、公开资产与重新下载摘要。Windows 下载沿用 0.1.34 并明确版本。
